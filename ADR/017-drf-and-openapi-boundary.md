# ADR 017: DRF and generated OpenAPI boundary

Status: Accepted on 2026-10-05 through the user's delegated implementation judgment. The user authorized continued development and delegated the DRF versus Ninja choice; this record identifies the selected option and its limits.

**Decision:** Use Django REST Framework with explicit serializers and `APIView` endpoints. Generate versioned OpenAPI with drf-spectacular from the DRF serializers, routes, and explicit schema annotations. Those definitions are the wire-contract authority; the generated document is a reviewable artifact, not a second manually maintained contract. The first increment's [OpenAPI](../artifacts/thesis-openapi.yaml) covers the thesis API; the subsequent [desk schema](../artifacts/desk-openapi.yaml) also covers paper positions. Ordinary Django session endpoints are documented in [API_DEVELOPMENT.md](../API_DEVELOPMENT.md). Independent Python domain modules remain authoritative for business rules. Do not adopt Ninja or Pydantic for this boundary.

**Why:** Conventional Django integration and explicit request, response, authentication, and permission handling fit the owner's maintenance and audit preferences. DRF 3.16 supports the selected Django 5.2 and Python 3.13 targets. DRF's built-in OpenAPI generator is deprecated and its documentation recommends drf-spectacular. These are compatibility and maintenance reasons, not measured performance or analysis-quality claims. [DRF compatibility](https://www.django-rest-framework.org/community/3.16-announcement/), [schema guidance](https://www.django-rest-framework.org/api-guide/schemas/)

**Input and authority:** Accept JSON through an explicit strict boundary: reject duplicate keys, non-finite values, unknown fields, and type coercion; preserve exact thesis text without trimming. Derive the actor from the authenticated session. Scope every read, creation, and mutation to that actor in the application service, including staff accounts. Permission classes alone do not filter private lists or establish creation authority. Session writes require CSRF; login requires Django's explicit CSRF protection. [Field behavior](https://www.django-rest-framework.org/api-guide/fields/#charfield), [permission limits](https://www.django-rest-framework.org/api-guide/permissions/#limitations-of-object-level-permissions), [session and login protection](https://www.django-rest-framework.org/api-guide/authentication/#sessionauthentication)

**Approval:** Store immutable draft text and a manually supplied concise interpretation, with their provenance visible. Approval binds both exact hashes and latest draft versions, derives authority from the session, and compares the expected aggregate revision under transaction protection. A stale browser cannot approve an obsolete draft or replace a newer approval. A retry returns the saved approval and its current disposition without reactivating historical state. Administrative inspection stays read-only; models and endpoints do not introduce a second approval path.

**Timing:** Sample the trusted approval clock after acquiring transaction protection. `approved_at` is the acceptance/effective timestamp within that protected operation; it does not prove the exact instant of durable visibility at commit. The manual interpretation's provisional `known_at` records preparation time and carries the same limitation, not the domain's completed durable-availability guarantee. This increment does not establish operational replay for these records or connect them to publication governing pins. That integration must establish durable availability and use the ADR 015 ordering protocol.

**First scope:** An authenticated JSON journey from immutable user draft and manual interpretation to explicit approval and private current/history inspection. History reads use a coherent read-only snapshot, cap each category at 100 records, and report truncation explicitly; complete history pagination must precede external use. It does not establish model compilation, source capture, attached paper-trade exposure, a TypeScript desk UI, global fan-out, live monitoring, or external delivery. Implementation and test evidence belongs in [IMPLEMENTATION.md](../IMPLEMENTATION.md).

**Schema verification:** Describe requests, successful responses, and failures explicitly, then generate and validate OpenAPI. Runtime tests still prove strict parsing, ownership, exact hashes, CSRF, and approval races; schema validation alone cannot prove them. TypeScript client/validator generation tooling remains open. [drf-spectacular workflow](https://drf-spectacular.readthedocs.io/en/latest/customization.html)

**Rejected for this increment:** Ninja's shorter typed endpoints do not justify adding Pydantic as another contract dependency for this small boundary. Automatic model CRUD and writable history would obscure the explicit approval service. A separately handwritten OpenAPI document would introduce competing schema authority.

**Still open:** Frontend tooling and TypeScript client generation; durable workers/queue; hosting and deployed authentication configuration; providers and source rights. Revisit the API choice if measured contract or maintenance costs warrant a superseding ADR.
